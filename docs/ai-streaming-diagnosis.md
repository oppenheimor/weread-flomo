# AI 等待体验实测

使用当前配置的 DeepSeek / deepseek-v4-pro，对同一章节做三次真实整理；不发送 flomo。测试前确认没有手动编辑的结果。前两次失败保留原结果，第三次成功。

## 观测

- 第一次：页面约 97.7 秒后报告连接失败，公开正文始终为零。原有错误信息不足以确定底层原因。
- 第二次（增加安全诊断）：请求后 626 ms 收到 SSE 响应头，2,198 ms 收到真实推理事件，113,078 ms 时发生 IOException；没有公开正文。客户端总时间含预览刷新，约 114.5 秒。
- 第三次：421 ms 收到 SSE 响应头，2,167 ms 开始推理，59,354 ms 收到首段公开正文，61,426 ms 完成。线上流量 1,364,756 字节，公开正文 1,320 UTF-8 字节（606 字符 JSON）。
- 第三次页面：点击后 61.25 秒首次出现卡片（含约 1.2 秒预览刷新）；草稿只有 4 次可见变化，约每 350–390 ms 更新一次；62.73 秒收到完成状态，最终显示 4 张卡片。最后的卡片在完成切换时一起出现。
- 公开正文渲染期间没有观测到超过 50 ms 的浏览器长任务；两次长任务发生在正文开始之前。因此目前证据指向长推理、粗粒度刷新与最终整批切换，不足以归因为 React CPU 性能瓶颈。

## 已修复

- 去掉等待提示处第二只猫，保留章节标题处头像。
- 推理事件只报告状态，不回传内部推理文本；无流式响应时明确说明等待完整结果。
- 将 SSE 线上传输上限（32 MB）和公开正文上限（2 MB）分离，保持单事件与总耗时边界。
- 新回归测试构造约 2.3 MB SSE 包装/推理流量、仅 6 字节正文，旧实现稳定抛出 `AI stream too large`，修复后通过；另测正文仍受 2 MB 上限保护。
- 该限额是确定存在的中断风险，但前两次调用没有记录原始异常消息，不能断言它就是两次失败的唯一原因。第三次流量未跨过旧上限，也不能据第三次成功声称首字等待已修复。
- 诊断仅记录耗时、字节数、状态、异常类型，不记录密钥、笔记或推理文本。

## 前三次测试后的待处理项（后续进展见下文）

- 模型约一分钟的首段正文等待仍存在。当前并未更改用户模型、关闭推理或伪造思考内容。
- 250 ms 后端快照与 350 ms 前端轮询只能捕获少量可见更新；最后完成状态仍可能带来数张卡片同时出现。应进一步改进增量传输和完成交接，不能只添加假打字动画或凭模拟截图声称顺滑。
- “思考状态”不等于可读的“整理思路”；若需要后者，应独立约定简短公开说明，而不是展示内部推理原文。

## 第四次：用户确认默认快速整理后

查阅 DeepSeek 官方 thinking_mode 文档，确认默认开启 high 思考，支持 `thinking.type=disabled/enabled`。对已确认支持的模型默认关闭思考，保留显式开启选项，未更换模型或修改账户配置。草稿写入改为 60 ms 上限，接收正文时客户端串行轮询改为 80 ms，并使用可被用户打断的平滑跟随。

同模型同章节单次真实实测：

- 响应头 480 ms，第一段公开正文 1,498 ms，模型完成 6,491 ms，没有推理阶段信号。
- 页面点击后约 2,567 ms 出现第一张卡片，6,651 ms 完成。
- 生成期间记录 13 次可见草稿更新，完成前已出现全部 5 张卡片，不再在最终切换时补出剩余卡片。
- 流量 147,209 字节，公开正文 2,182 UTF-8 字节（1,114 字符 JSON）。
- 此次浏览器在前约 3 秒有多个 50–105 ms 长任务，不能宣称所有卡顿已消除；后续正文更新更密集。速度数字是单次观测，不是延迟保证。模型模式和源内容均会影响耗时。
- 未发送 flomo；没有为改善观感编造文字或插入打字延迟。
